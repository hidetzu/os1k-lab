# 07 カーネルパニック

教材：[カーネルパニック | OS in 1,000 Lines](https://operating-system-in-1000-lines.vercel.app/ja/07-kernel-panic)

## カーネルパニックとは

カーネルが、続行できないエラーに出会ったときに発生する。カーネルはそれ以上動くのをやめ、何が起きたかを表示して止まる。

## PANIC マクロ

`kernel.h` に書いた。

```c
#define PANIC(fmt, ...)                                                        \
    do {                                                                       \
        printf("PANIC: %s:%d: " fmt "\n", __FILE__, __LINE__, ##__VA_ARGS__);  \
        while (1) {}                                                           \
    } while (0)
```

`kernel.c` では、`.bss` を 0 で埋めた直後に呼んでいる。

```c
void kernel_main(void) {
    memset(__bss, 0, (size_t) __bss_end - (size_t) __bss);
    PANIC("booted!");
    printf("unreachable here!\n");
    ...
```

出力の形は `PANIC: ファイル名:行番号: メッセージ`。

- `"PANIC: %s:%d: " fmt "\n"`：C では、並べて書いた文字列リテラルはコンパイル時に1つにつながる。`fmt` も文字列リテラルなので、`"PANIC: %s:%d: booted!\n"` という1つの書式文字列になる。
- そのため `fmt` には文字列リテラルしか渡せない。`char *` の変数を渡すとコンパイルエラーになるはず（推論、未確認）。

## なぜ関数ではなくマクロなのか

`__FILE__` と `__LINE__` は、プリプロセッサが「その場所」のファイル名と行番号に置き換える。

- マクロは、使った場所に展開されてから置き換えられる。だから `PANIC` を呼んだ行の番号になる。
- 関数の中に `__LINE__` を書くと、その関数を定義した行の番号に固定される。どこから呼んでも同じ番号しか出せない。

観察では、`kernel.h` の行ではなく、`kernel.c` で `PANIC("booted!")` を書いた32行目が出た（「観察結果」）。

## マクロを安全に書くための書き方

ここは一般知識で、規格や GCC の文書の該当箇所は未確認。

### do { ... } while (0)

マクロの中身を、1つの文として扱えるようにする書き方。

```c
if (error)
    PANIC("oops");
else
    printf("ok\n");
```

中身を `{ ... }` だけで囲むと、展開後は `{ ... };` となり、`;` が余分な空の文になって `else` と対応が取れずコンパイルエラーになる。`do { ... } while (0)` なら、使う側が付けた `;` でちょうど1つの文として閉じる。`while (0)` なので中身は1回だけ実行される。

### 行末の \

マクロの定義は本来1行。行末に `\` を置くと、次の行に続けて書ける。

### ##__VA_ARGS__

- `...` と `__VA_ARGS__`：可変長引数のマクロ。`...` に渡された引数が `__VA_ARGS__` に入る。
- `PANIC("booted!")` のように追加の引数がないと、`__VA_ARGS__` は空になり、`__LINE__, )` と余分な `,` が残ってしまう。
- `##` を付けると、`__VA_ARGS__` が空のときに直前の `,` を取り除く。GCC の拡張で、clang も対応している。C23 では標準の `__VA_OPT__` で同じことができる。

## どう止まるか

`PANIC` は最後に `while (1) {}` で止まる。

| 止め方 | 使っている場所 | ホストの CPU 使用率（`top` の `qemu-system-riscv32`） |
| --- | --- | --- |
| `while (1) {}` | `PANIC` | 100%（2026-11-22 観察） |
| `for (;;) { wfi }` | `kernel_main` の最後 | ほとんど出てこない（`hello-world.md` で観察） |

`PANIC` はカーネルを止めるが、CPU は休んでいない。`hello-world.md` で試した空ループと同じ止まり方。

## 観察結果

2026-11-22、ホストの Arch で観察。

### 実行（./run.sh）

```
PANIC: kernel.c:32: booted!
```

予想どおりだったこと：

| 確かめたこと | 結果 |
| --- | --- |
| 行番号 | `32`。`kernel.c` の32行目がちょうど `PANIC("booted!");` |
| `unreachable here!` | 出ない |
| `top` で見た CPU 使用率 | 100% |

教材の出力例は `kernel.c:46` だが、行番号は自分のコードの書き方で変わる。

### 読み取り

- `jal printf` は1回だけで、渡している引数は `PANIC` の書式・`"kernel.c"`・`32`。これは `PANIC` の中の `printf`。
- `unreachable here!` の `printf` は命令に残っていない。文字列も `.rodata` のどこにもない。
- `wfi` のループも消えている。`0x80200058` の自分自身へのジャンプのあとには何もない。
- 推論：clang は `while (1) {}` から抜けられないと判断し、その後ろのコードと、そこでしか使わない文字列を取り除いた（`-O2`）。
- `__FILE__` と `__LINE__` はコンパイル時に決まった値になっている。`"kernel.c"` は `.rodata` の文字列、`32` は `li a2, 0x20` という即値。
- 書式の文字列は `"PANIC: %s:%d: "` と `"booted!"` と `"\n"` がつながった1つの文字列になっている。
- `.bss` は空（`__bss` と `__bss_end` が同じ `0x8020_02b4`）なので、`memset` は 0 バイトを埋める呼び出しになっている。
