## この章の「メモリ」は何を指すか

最初の予想は「物理的なメモリと、プログラムから使えるメモリの区別が必要」だった。この章の番地は、すべて物理アドレスのまま。

09 章で分けているのは、同じ物理 RAM の中の次の2つ。

| 区分                                   | 誰が決めるか  | いつ決まるか | 中身                                                   |
| -------------------------------------- | ------------- | ------------ | ------------------------------------------------------ |
| 置き場所が決まっている部分             | `kernel.ld`   | リンク時     | カーネルの命令・データ・`.bss`・スタック               |
| あとから配る部分（この章の「メモリ」） | `alloc_pages` | 実行時       | ページテーブル、プロセスのスタックなど（後の章で使う） |

### 物理 RAM の配置

QEMU virt の RAM（`0x8000_0000`〜`0x87ff_ffff`、128MiB）の中で、何がどこにあるか。`__free_ram` と `__free_ram_end` は、自分の環境でも教材と同じ番地だった（「観察結果」）。

```
物理アドレス     RAM の中身
0x8000_0000     +----------------------+
                | OpenSBI              |   QEMU が置く（boot.md）。〜0x8004_ffff。S-mode からは触れない
                +----------------------+
                | (unused)             |
0x8020_0000     +----------------------+ -+
                | .text .rodata .data  |  |
                | .bss                 |  |  kernel.ld が番地を決め、QEMU が ELF を読み込む
                | stack 128KB          |  |
__stack_top     +----------------------+ -+
                | (padding to 4KB)     |
__free_ram      +----------------------+ -+  0x8022_1000
                |                      |  |
                | free RAM 64MB        |  |  ★ この章の「メモリ」
                | alloc_pages hands    |  |  kernel.ld は範囲を決めるだけ。
                | out pages from here  |  |  実行時に alloc_pages が先頭から順に配り、0 で埋める
                |                      |  |
__free_ram_end  +----------------------+ -+  0x8422_1000
                | (unused)             |
0x87e0_0000     +----------------------+
                | device tree          |   QEMU が置く（boot.md）
0x8800_0000     +----------------------+   RAM の終わり
```

（日本語や罫線の文字は、表示する環境によって幅が変わって図がずれるので、箱の中は ASCII だけで書き、説明は箱の外に置いた。）

## kernel.ld の変更

`__stack_top` の後ろに4行を足した。

```
    . = ALIGN(4096);
    __free_ram = .;
    . += 64 * 1024 * 1024; /* 64MB */
    __free_ram_end = .;
```

### 前提：`.` は「次に物を置く番地」

`kernel.ld` は、上から順に「現在地 `.`」を動かしながらメモリに物を並べていく手順書として読む。

| 書き方            | 意味                                                                                     |
| ----------------- | ---------------------------------------------------------------------------------------- |
| `. = 0x80200000;` | 現在地をその番地に移す                                                                   |
| `.text : { ... }` | 現在地にセクションの中身を置き、置いた分だけ現在地を進める                               |
| `. = ALIGN(n);`   | 現在地を、n の倍数になるまで切り上げる                                                   |
| `. += n;`         | 何も置かずに、現在地を n バイト進める（場所の予約）                                      |
| `__名前 = .;`     | 今の現在地に名前（シンボル）を付ける。C からは `extern char __名前[]` で番地として使える |

### 1行ずつたどる

2026-11-22、ホストの Arch で、この時点のコード（`alloc_pages` を足す前）と `kernel.ld` をビルドして番地を確かめた。`alloc_pages` を足すと命令が増えるので、`__free_ram` より前の番地は少しずれる。

| 行                                | 実行後の `.`  | 何が起きたか                                                            |
| --------------------------------- | ------------- | ----------------------------------------------------------------------- |
| `. = 0x80200000;`                 | `0x8020_0000` | 出発点。OpenSBI が飛んでくる番地                                        |
| `.text`                           | `0x8020_0338` | 命令を `0x338` バイト置いた（先頭は `boot`）                            |
| `.rodata : ALIGN(4)`              | `0x8020_038f` | 4 の倍数にそろえてから、文字列などを `0x57` バイト置いた                |
| `.data : ALIGN(4)`                | `0x8020_038f` | 中身がないので進まない                                                  |
| `.bss : ALIGN(4)` と `__bss = .;` | `0x8020_0390` | 4 の倍数に切り上げ。`.bss` は空なので `__bss` と `__bss_end` は同じ番地 |
| `. = ALIGN(4);`                   | `0x8020_0390` | すでに 4 の倍数なので変わらない                                         |
| `. += 128 * 1024;`                | `0x8022_0390` | 何も置かずに 128KB（`0x2_0000`）進める。ここがスタック                  |
| `__stack_top = .;`                | `0x8022_0390` | スタックの上端に名前を付ける                                            |
| `. = ALIGN(4096);`                | `0x8022_1000` | 4KB の倍数に切り上げる（`0x390` → `0x1000`）                            |
| `__free_ram = .;`                 | `0x8022_1000` | 空き RAM の始まりに名前を付ける                                         |
| `. += 64 * 1024 * 1024;`          | `0x8422_1000` | 何も置かずに 64MB（`0x400_0000`）進める                                 |
| `__free_ram_end = .;`             | `0x8422_1000` | 空き RAM の終わりに名前を付ける                                         |

`llvm-nm -n kernel.elf` の結果も、この表と一致した。

```
80200000 T boot
80200390 B __bss
80200390 B __bss_end
80220390 B __stack_top
80221000 B __free_ram
84221000 B __free_ram_end
```

図との対応：

```
0x8020_0000     +----------------------+  <- . = 0x80200000
                | .text .rodata        |  <- 中身を「置いた」部分（ELF に入る）
0x8020_0390     +----------------------+  <- __bss = __bss_end
                | stack 128KB          |  <- . += 128KB（予約しただけ）
0x8022_0390     +----------------------+  <- __stack_top
                | (padding to 4KB)     |  <- ALIGN(4096) で飛ばした隙間
0x8022_1000     +----------------------+  <- __free_ram
                | free RAM 64MB        |  <- . += 64MB（予約しただけ）
0x8422_1000     +----------------------+  <- __free_ram_end
```

- `. += n` は「場所を空けて、名前を付けるだけ」。スタックも空き RAM も、`kernel.ld` は番地の範囲を決めるだけで、中身は何も置いていない。実際に使うのは実行時のコード（スタックは `boot` が `sp` に設定し、空き RAM は `alloc_pages` が配る）。
- 教材の `__free_ram` も `0x8022_1000` だった。推論：4KB 境界に切り上げるので、手前の大きさが多少違っても同じ番地になった。
- `ALIGN(4096)` にするのは、`alloc_pages` が 4KB のページ単位で配るため。先頭がそろっていれば、配る番地がすべて 4KB 境界になる。

### .text / .rodata / .data / .bss の役割

プログラムの中身を、「何を入れるか」と「書き換えてよいか」で4つに分けたもの。

| セクション | 入るもの                                               | 書き換え | ELF ファイルに中身があるか |
| ---------- | ------------------------------------------------------ | -------- | -------------------------- |
| `.text`    | 命令（関数の本体）                                     | しない   | ある                       |
| `.rodata`  | 書き換えない定数（read-only data）。文字列リテラルなど | しない   | ある                       |
| `.data`    | 最初の値が決まっている（0 以外の）グローバル変数       | する     | ある                       |
| `.bss`     | 最初の値が 0（または値を書いていない）のグローバル変数 | する     | ない（大きさだけ記録）     |

自分のコードで言うと：

```c
void kernel_main(void) { ... }               // .text：命令
printf("1 + 2 = %d, %x\n", ...);             // .rodata：書式の文字列
"0123456789abcdef"[nibble]                   // .rodata：printf の中の文字列

int counter = 5;                             // .data（今のコードにはない）
int buffer[1024];                            // .bss（今のコードにはない）
```

- 07 章で見た `.rodata` には、`kernel.c`、`PANIC: %s:%d: booted!`、`0123456789abcdef` が並んでいた（`kernel-panic.md`）。
- 今のコードにはグローバル変数がないので、`.data` は空、`.bss` は大きさ 0。

#### .bss だけ特別な理由

- `.bss` の中身は全部 0 なので、ELF ファイルに 0 を並べて保存せず、「この番地から何バイト」という大きさだけを記録する。`llvm-readelf -S` で、`.bss` の種類は `NOBITS`（ファイルに中身なし）、`.text` と `.rodata` は `PROGBITS`（ファイルに中身あり）だった。
- その代わり、実行前に誰かがその範囲を 0 で埋める必要がある。04 章から `kernel_main` の最初でやっている `memset(__bss, 0, ...)` がその仕事（`boot.md`）。

#### 分ける理由

- 守るため：`.text` と `.rodata` は書き換えないので、読み取り専用にできる。推論：ページテーブルの章で、ページごとに「読み取り専用」「実行してよい」といった権限を付けるときに効いてくる。
- ファイルを小さくするため：`.bss` の中身をファイルに持たずに済む。

## alloc_pages

`kernel.c` に書いた。`PAGE_SIZE`（4096）は `common.h` に足した。

```c
extern char __free_ram[], __free_ram_end[];

paddr_t alloc_pages(uint32_t n) {
    static paddr_t next_paddr = (paddr_t) __free_ram;
    paddr_t paddr = next_paddr;
    next_paddr += n * PAGE_SIZE;

    if (next_paddr > (paddr_t) __free_ram_end)
        PANIC("out of memory");

    memset((void *) paddr, 0, n * PAGE_SIZE);
    return paddr;
}
```

- 4KB のページを `n` 枚配り、先頭の物理アドレスを返す。
- `next_paddr` は「次に空いている番地」。最初は `__free_ram` で、配るたびに `n * PAGE_SIZE` だけ前へ進めるだけ。
- 空き RAM の終わり（`__free_ram_end`）を超えたら、0 を返すのではなく `PANIC` する。戻り値の確かめ忘れによる、追いにくいバグを避けるため。
- 返す前に、配る範囲を `memset` で 0 にする。呼び出し側が初期化を忘れても、前の中身が残らない。
- 返却（解放）の仕組みはない。一度配ったページは戻ってこない。教材は、後から作る方法としてビットマップやバディシステムを挙げている。

```
next_paddr の動き（ページ = 0x1000 バイト）

0x8022_1000  +---------+  <- 最初の next_paddr = __free_ram
             | paddr0  |  alloc_pages(2)：2 ページ
             | (2 pg)  |
0x8022_3000  +---------+  <- 1 回目のあとの next_paddr
             | paddr1  |  alloc_pages(1)：1 ページ
0x8022_4000  +---------+  <- 2 回目のあとの next_paddr（次はここから）
             |  ...    |
0x8422_1000  +---------+  <- __free_ram_end（超えたら PANIC）
```

### 補足：メモリ割り当てのアルゴリズム

ここは一般知識の整理で、教材が触れているのはバンプ方式（この章の方式）と、後から作る方法として名前を挙げたビットマップとバディシステムだけ。各方式の細かい動きは、文献で確かめていない。

| 方式 | 仕組み | 返却 | 速さ | 弱点 |
| --- | --- | --- | --- | --- |
| バンプ（この章） | 「次の空き」を指すポインタを進めるだけ | できない | 最速（足し算1回） | 使い終わったメモリが戻らない |
| フリーリスト | 空いている範囲を連結リストでつなぎ、合う大きさのものを探して切り出す | できる | 探す分だけ遅い | 小さな隙間が散らばる（断片化） |
| ビットマップ | 1 ページに 1 ビットを割り当て、0 = 空き、1 = 使用中で管理する | できる | 空きビットを探す分だけ遅い | 連続した多くのページを探すのが苦手 |
| バディシステム | 2 の累乗の大きさのかたまりで管理し、半分ずつ分けて配る。返ってきた隣同士（バディ）がそろえば合体させる | できる | 速い | 2 の累乗に切り上げる分の無駄 |
| スラブ | 同じ大きさの小さなもの（構造体など）用に、ページを同じ大きさの区画に分けて使い回す | できる | 速い | 決まった大きさのものにしか向かない |

それぞれのイメージ：

```
バンプ：ポインタが前に進むだけ
  [used][used][used] | free ...
                     ^ next_paddr

ビットマップ：ページごとに 1 ビット
  page:  0 1 2 3 4 5 6 7
  bit:   1 1 0 1 0 0 0 1      0 = 空き。連続 3 ページなら 4〜6 を使う

バディシステム：半分ずつ分けて配り、返ってきたら合体させる
  [            16 pages            ]
  [    8 pages    ][    8 pages    ]
  [ 4 pg ][ 4 pg  ][    8 pages    ]
  4 ページの依頼 → 16 を 8 + 8 に、さらに 8 を 4 + 4 に分けて、4 ページを 1 つ配る
```

- この OS でバンプ方式で済むのは、長く動かし続けることを想定していないから（教材より）。返却がないので、動かし続けると、いつか `out of memory` になる。
- 一般の OS では、ページ単位の割り当てにバディシステムを使い、その上に小さなもの向けのスラブを重ねる組み合わせがよく知られている（一般知識。Linux はこの形とされる）。
- C の `malloc` はページより小さい単位で配るので、OS からまとめてページをもらい、その中をフリーリストなどで切り分けている（一般知識）。

### next_paddr はどこに置かれるか

関数の中の `static` 変数は、関数を抜けても値が残り、グローバル変数と同じ場所（`.data` か `.bss`）に置かれる。最初の値が `__free_ram` の番地（0 ではない値）なので、`.data` に入るはず（「.text / .rodata / .data / .bss の役割」の表から）。観察結果で確かめた。

## 『はじめて読む486』との対応

第3章 3.3節「メモリ管理」（p.72〜）。ページは本に印刷されている番号。

| 486 本の項目 | ページ | 内容 | この章との対応 |
| --- | --- | --- | --- |
| 3.3 冒頭 | p.72 | OS のメモリ管理には「メモリ割り当て」「メモリ保護」「仮想記憶」の3つの役割がある。後の2つは MMU というハードウェアの助けが要る | この章で作ったのは「メモリ割り当て」だけ |
| メモリ割り当て | p.73 | メモリを、OS が使う「システム領域」と、アプリが使う「ユーザー領域」に分け、OS がユーザー領域を割り当てる。マルチタスクでは複数のタスクに分配する | 「置き場所が決まっている部分」（`kernel.ld`）と「あとから配る部分」（`alloc_pages`）の分け方に近い |
| メモリ保護 | p.74 | 項目名のみ確認 | この OS にはまだない |
| 連続したメモリ領域の確保 | p.85 | 要求と返却を繰り返すとメモリが虫食いになり、空きの合計は足りていても連続した大きな領域を渡せなくなる。MMU の番地の変換で、小さな領域をつないで連続しているように見せられる | 「補足：メモリ割り当てのアルゴリズム」の断片化。返却できないバンプ方式では、この問題はまだ起きない |
| 仮想記憶、MMU による仮想記憶 | p.86〜89 | 実際より多くのメモリがあるように見せる | 最初の予想（物理メモリとプログラムから見えるメモリの区別）に近い |

- ビットマップやバディシステムのような、具体的な割り当てのアルゴリズムは載っていなかった。
- 共通する考え方：OS がメモリの使い道を管理し、プログラムに配る。
- 機種固有の仕組み：486 は MMU を CPU に内蔵し、セグメントとページングで保護と変換を行う。RISC-V の仕組みは、この章ではまだ使っていない。

## 観察結果

2026-11-22、ホストの Arch で観察。

### シンボル（llvm-nm kernel.elf）

```
80221000 B __free_ram
84221000 B __free_ram_end
802004dc d alloc_pages.next_paddr
```

- `__free_ram` と `__free_ram_end` は、教材と同じ `0x8022_1000` と `0x8422_1000`。
- `next_paddr` の記号は `d`。`.data` に入っている（小文字は、ファイルの外から見えないローカルなシンボル）。最初の値が 0 ではないので `.bss` ではなく `.data`、という予想どおり。

### 実行（./run.sh）

`kernel_main` で `alloc_pages(2)`、`alloc_pages(1)` の順に呼び、番地を表示してから `PANIC("booted!")` で止めた。

```
alloc_pages test: paddr0=80221000
alloc_pages test: paddr1=80223000
PANIC: kernel.c:135: booted!
```

| | 値 | 読み方 |
| --- | --- | --- |
| `paddr0` | `0x8022_1000` | `__free_ram` と同じ。最初の呼び出しは空き RAM の先頭を返す |
| `paddr1` | `0x8022_3000` | `paddr0` から `0x2000`（2 ページ × `0x1000` = 8192 バイト）進んだ番地 |

教材の出力例（`80221000` と `80223000`）とも一致した。

最初は差を `0x200` と数え間違えた。16 進数では `0x8022_1000` のように 4 桁ずつ `_` で区切ると、0 の数を数え間違えにくい。
